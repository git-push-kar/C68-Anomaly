# Paper-level benchmarking of the prose source: implementation plan

Status: **plan and discussion record, not a pre-registration and not a result.** Nothing described
here has been run, trained, generated or scored. It consolidates `docs/PROTOCOL.md` §29 and §30, the
six execution plans in `docs/PROSE_SOURCE_EXECUTION_PLANS_V1.md`, the follow-up specification, and
the working discussion of 2026-11-04. Where this document and a dated protocol section disagree,
the dated section wins; the places where this document *proposes* to change one are collected in §8
and marked as proposals, never as decisions.

The open question it answers: §30 is paper-level in method and not in scope. This document sets out
what has to be built for the comparison to survive review as a benchmark rather than an ablation,
and which of those items are still undecided.

---

## 1. The question, and the boundary of the claim

The claim under test: **which writer supplies the report prose for the three open strata — a
deterministic assembler, the adapter, a hybrid, a retrained adapter — and at what defect rate and
cost.** A second, separate claim covers the follow-up surface.

The boundary, which does not move:

| layer | what it is | can prose change it? |
|---|---|---|
| prose quality and defect rate | cells, flags, anchor, preference | **yes — this study** |
| system benchmark | fault classification, abstention, calibration | no |
| end-to-end operation | latency, cost per report, operator time | indirectly |

Diagnosis, verdict, severity and confidence are code outputs in every condition (§29.1). No
condition in this plan may change them, and no result here may be reported as a change in accuracy.
A paper needs both tables — how well the system diagnoses, and which writer produces the better
report at what cost — but only the second belongs to this study; the first is the folds/baselines
and calibration-refit track.

## 3. The design under discussion

### 3.1 Three surfaces, three instruments, no pooling

| surface | conditions | measurement set | gate family |
|---|---|---|---|
| report | A, B, C, missing cell, D, E | 520 items × 3 orders | prose gates (§29.5 / §28) |
| follow-up | template-only, adapter as-is, F | 97-row `prose_eval_followups.jsonl` | follow-up gates (`docs/TRAINING_SPEC_FOLLOWUP_V1.md`) |
| deployment | stratified routing vs A | one 10-row stratum | **descriptive only** |

Results never cross surfaces. The report is *context* for a follow-up turn; a follow-up gate cannot
stand in for a report gate, and a routing observation on ten rows cannot become a deployment rule.

### 3.2 The closed grid

The grid is the report-surface 2×2 over who writes which part, plus two toggles:

| | numbers by code | numbers by adapter |
|---|---|---|
| **mechanism by code** | **A** fallback v3.1 | **M** missing cell (B's mechanism, A's numbers) |
| **mechanism by adapter** | **C** hybrid | **B** full adapter |

| toggle | what it isolates | cost |
|---|---|---|
| **D** vs B | the check-retry-fallback wrapper, identical prose | 0 GPU; stored text |
| **E** vs B | training for report prose, 3 seeds | 3.0–5.2 h |

"Closed" means the grid is fixed before the first run and nothing is added or dropped afterwards.
Contrasts then name their own primary outcome, because the metrics do not apply uniformly: A, M and
C all have code-written numbers, so a numeric-defect contrast between them cannot be decided on
numeric-defect rate and must be decided on preference and tag role.

### 3.3 One primary contrast

Twelve conditions give 66 pairwise comparisons, which is not a multiplicity problem to be corrected
— it is a design that has no primary. The proposal:

- **primary: B vs A on numeric-defect rate**, paired per item. This is the decision the deployment
  actually faces.
- **secondary, Holm-controlled:** C vs B, M vs B, D vs B, E vs B, anchor, grounding, tag role,
  preference, fallback rate, cost per 1,000 reports.
- **descriptive, no p-values:** per-stratum counts, routing on the 10-row stratum, per-order
  variation.

### 3.4 The selection rule, declared before results

The winner is chosen by a written rule, not by reading the table:

1. fewest **numeric-defect rows** on the fit set (primary);
2. tie → higher **preference** among blind-rated rows;
3. tie → lower **cost per 1,000 reports**;
4. tie → **A**, because determinism is the conservative default.

This exists because selection inflates the selected condition's reported level (§6.3). With the rule
written down, running twelve cells creates no selection bias at all: there is no choice left to be
biased toward.

### 3.5 The confirmatory pass

One pass on the test set, once, **winner plus A**, paired:

| property | value |
|---|---|
| conditions | the selected condition and A |
| items | the test export, once (§29.3, §29.8) |
| statistic | exact McNemar on per-item numeric flags; paired bootstrap CI on the risk difference |
| receipt | config hash, item hash, model revision, timestamps, written before the pass and stored beside it |
| permitted outcome | the winner's confirmatory claim. A second pass is a new dated section |

A is deterministic and free, so pairing costs nothing and converts a point estimate into a
contrast on data neither condition was selected on.

### 3.6 What "all combinations" cannot mean

The instruction "implement A to F and their combinations, then take the best" is right about
breadth and wrong about search. Four reasons, none of them budgetary:

1. **They are not one grid.** D is a delivery wrapper on B, not a writer axis. E is a checkpoint, not
   a writer. F lives on another surface with another gate family. Enumerating all six as factors
   manufactures cells that are not interpretable and pairs that cannot be scored by one instrument.
2. **Per-cell n collapses.** Twelve disjoint cells over 520 items is 43 items per cell, which carries
   no claim. The grid must be **paired**: every condition scored on every item.
3. **Multiplicity without a primary** is not a correction, it is a design fault; correcting 66
   comparisons destroys power for the one that decides the deployment.
4. **A search cannot be pre-registered**, because its content is "react to the results" — the one
   thing §30.4 and §30.6 forbid.

Breadth is still worth having, for a reviewer-facing reason: the first question about a two-condition
study is "why not the other four?" A closed declared grid with intervals answers it before it is
asked.

## 4. The instrument defect that gates every number

### 4.1 Mechanism

`scripts/pilot_rechecks.py` `numeric_flags` (line 200) splits a sentence, collects **every detector
named in it**, and then, for each detector, searches `above|below` over **the whole sentence**
(lines 235–237). A sentence that names two detectors with opposite directions therefore satisfies
both branches by construction. The training example is v5-05: "The CVA Q-statistic (186.9) is below
threshold (194.6), and the LSTM autoencoder reconstruction error (0.7026) is only slightly above
threshold (0.6870)" — both inequalities are true, and both detectors get flagged.

### 4.2 Scale of the effect

| reading | value |
|---|---|
| adapter numeric flags of kind `wrong_inequality_direction` | **47** |
| numeric rows where that kind is the first cause | 27 of 62 |
| occurrences of the mixed-direction sentence shape (top table, §7) | 88, plus variants of 28 / 18 / 18 / 15 / 6 / 6 |
| other numeric kinds | `value_not_stored` 34, `threshold_misquoted` 1 |

So the dominant family in the **primary outcome** is the shape that the instrument is known to
misread. The measurement cannot be quoted before the binding is fixed.

### 4.3 Proposed repair

1. Bind the comparator to the clause that mentions the detector — split on `, and` / `;` /
   sentence end and evaluate the direction word only inside the detector's own clause — instead of
   evaluating sentence-wide.
2. Extend `scripts/recheck_cases.py` from 40 to 46 cases with the four known false-positive
   families: mixed-direction sentence, stored-value restatement (`-2.48%`, `z=-0.24`), tag cited
   only inside a hypothetical, and `XMV` as valve position.
3. Re-run the calibration. Acceptance is precision 1.00 and recall 1.00 on 46 cases; anything less
   blocks the study.
4. Re-measure the 520 rows and record the new reading as a **new dated artefact**, leaving the old
   one in place. The 28.9 calibration is not edited retroactively.
5. Bracket whatever residual false positives survive, by sensitivity analysis, and report both
   readings in the paper.

### 4.4 The consequence for the clarification set

§30.4 item 12 currently recommends **bracketing, not correcting**, on the ground that correcting
would invalidate the 28.9 calibration. Given §4.2, bracketing alone leaves the primary outcome
dominated by an artefact. This document therefore **proposes** item 12 be restated as: correct the
comparator binding, extend and re-run the calibration to 46 cases, and bracket the residual. It is
listed as decision **D6** in §8 and is not in force until signed.

## 6. Measurement and statistics, in full

### 6.1 Metrics

| metric | denominator | direction |
|---|---|---|
| numeric-defect rows | 520 per order | lower |
| grounding rows | 520 | lower |
| tag_role rows | 520 | lower |
| contradiction rows | 520 | lower |
| anchor exact, top \|z\| ≥ 1 | rows with top \|z\| ≥ 1 (329) | higher |
| schema-valid, complete | 520 | higher |
| empty narrative | 520 | lower |
| over-refusal / refusal | follow-up turns by class | lower / higher |
| preference | blind-rated pairs | higher |
| fallback rate | delivered rows | lower |
| latency, VRAM, $ per 1,000 | measured harness | lower |

Delivered text is what is measured, never first attempts (§29.4). Rows are paired by `item_id`
across conditions, which is what the join check already establishes.

### 6.2 Tests, multiplicity and power

- paired per-item flags → **exact McNemar** per check;
- risk difference with a **paired bootstrap** CI (10,000 resamples, seeded);
- one primary, secondaries under **Holm**;
- **minimum detectable difference stated before the run**. Exact McNemar at n = 520 with a 15%
  discordance rate reaches 80% power at a 4.9-point difference (4 points gives 63%, 6 points 94%);
  at n = 200 even 6 points reaches only 53%. That is the arithmetic behind decision D1, not a
  preference for round numbers;
- per-stratum results are **counts**, never tests: 10-row cells cannot carry a claim;
- three seeds for the shipped condition, reported as mean and range, not as a single run.

### 6.3 Winner's curse, quantified

Selection bias grows with the number of candidates. Simulated with paired, correlated conditions
(shared item difficulty), n = 520, 4,000 replications, illustrative true rates with B at 12% and the
other cells at 4–5%:

| candidate set | optimistic bias on the selected condition | P(selecting a non-best condition) |
|---|---|---|
| 2 conditions, 8-point true gap | 0.03 pts | 0% |
| 4 cells (A, B, C, M) | 0.54 pts | 52% |
| 6 conditions | 0.70 pts | 49% |
| 12 conditions | 1.24 pts | 89% |

For scale: one condition's standard error is 0.86 points at a 4% rate and 1.42 points at 12%. The
inflation is therefore the same order as the gaps between the near-tied cells. **A vs B is safe on
fit data; C vs M vs A is a coin flip, and only the confirmatory pass of §3.5 can decide it.** That
is the argument for declaring the rule and for pairing the test pass — not an argument against
running the grid.

Reproduce with:

```python
import numpy as np
rng = np.random.default_rng(7); grid = np.random.default_rng(0).normal(size=400000)

def sim(rates, n=520, reps=4000):
    cuts = np.array([np.quantile(grid, p) for p in rates])
    bias, picks, wrong = [], np.zeros(len(rates)), 0
    for _ in range(reps):
        u = rng.normal(size=n)
        z = 0.8 * u + 0.6 * rng.normal(size=(len(rates), n))
        obs = (z < cuts[:, None]).mean(1)
        j = int(np.argmin(obs))
        bias.append(obs[j] - rates[j]); picks[j] += 1
        wrong += j != int(np.argmin(rates))
    return np.mean(bias), picks / reps, wrong / reps
```

### 6.4 What is not measured

- The classification, abstention and calibration tables: prose cannot move them.
- Per-stratum contrasts, including routing: descriptive counts only.
- Post-hoc repair and stratified routing **as conditions**: recorded as non-conditions (§30.2) so they
  cannot be introduced later as though pre-registered.

## 9. Risks and limitations, stated rather than worked around

| limitation | consequence | handling |
|---|---|---|
| no field or plant data anywhere in the project | all evidence is Tennessee Eastman simulation output | stated in the paper's data section; no transfer claim |
| faults 21 and 22 are synthetic | two of 22 classes have no real run | labelled `synthetic` wherever shown |
| the open-set condition is constructed by removing the true menu entry | `UNCLASSIFIED_OPEN_SET` is the accepted answer, not the generating fault | declared as construction, not as a natural prevalence |

| training targets were not guaranteed arithmetically sound | distillation transfers reasoning shape, not numeric correctness | the empirical basis for C over E; stated plainly |

| `outputs/` is gitignored | no artefact is citable as shipped | build 9 defines the release set |
| instrument false positives | a flag is a searchlight, not an oracle | fix, extend calibration, bracket the residual, report both readings |

| 6 — follow-up | template vs adapter vs F against the follow-up gates on 97 turns |

Sentences the design is built to support, and the ones it cannot:

- supported: "on 520 paired items the deterministic assembler produced fewer numeric defects than
  the adapter, and the difference persisted on the test pass (paired, exact p reported)";
- supported only if E runs: "training the adapter on report prose did not close the numeric gap";
- **not** supported by this study: any statement that prose changed diagnosis, verdict, severity or
  confidence.

## 11. Prohibitions

- No condition runs before D1–D4 and D6 are signed and dated.
- No cell, primary outcome, stage size or selection rule changes after any result is visible.
- No condition is measured on the test set except the single pass of build 8.
- Post-hoc repair and stratified routing are never introduced as conditions after the fact.
- E does not proceed without explicit approval.
- No condition may change the diagnosis, verdict, severity or confidence.
- A superseding result is a **new dated section**, never an edit of §29.9 or §30.
